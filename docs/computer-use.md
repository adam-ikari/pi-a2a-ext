# 与 computer use 的区别

computer use 让模型看屏幕猜坐标去点按，本桥让调用方按名字调工具、由宿主代跑。两者操作的不是一个东西：前者落在像素上，后者落在宿主会话里已经注册好的工具上。

## 机制差别

| | computer use | 本桥（MCP `tools/call`） |
| --- | --- | --- |
| 模型发出的东西 | 坐标与按键（`click(640,412)`） | 工具名 + 结构化参数（`{"name":"read","arguments":{...}}`） |
| 谁来执行 | 注入的输入事件，落到目标应用 | 宿主 `Main` 会话的 `getToolByName(name).execute()` |
| 模型看到的结果 | 截图，像素 | 工具的真实返回值（文本 / 图片） |
| 目标从哪来 | 屏幕上有什么就点什么 | `tools/list` 的目录（宿主注册表，原样透传） |
| 参数怎么定 | 靠视觉估计 | JSON Schema 2020-12，由宿主 typebox schema 导出 |
| 被操作的一方是否推理 | 要，模型得先看懂屏幕 | **不推理**（收请求 → 跑工具 → 回结果） |

实际差别落在两处：

**执行的是真工具，不是模拟操作。** `{"name":"read","arguments":{"path":...}}` 走的是宿主原生 `read` 的实现，执行落在宿主真实的文件与 shell 上。它不需要先有个窗口摆在那里，也不需要那个程序支持无头运行。

**目录是显式的，不是猜的。** `tools/list` 返回 `name` / `description` / `inputSchema`，调用方给的是名字和参数；坐标点击则要求模型先看出屏幕上有什么、算出像素位置。名字不在注册表里会得到 `not exposed`——未注册与不存在共用同一文案，不泄露这个名字是否本该存在；坐标点错就是点到了别的东西。

## 代价

| | computer use | 本桥 |
| --- | --- | --- |
| 上下文开销 | 每次交互都要带一张截图 | 只有工具返回值 |
| 宿主 token | 消耗 | 不消耗（不推理） |
| 稳定性 | 受布局、缩放、主题、焦点影响 | 受工具与参数校验影响 |
| 前提 | 目标应用有可见界面 | 工具在宿主注册表里 |

工具返回值仍然会进调用方的上下文——`read` 一个大文件或 `bash` 跑一次 `cat`，字节都在结果里，大件走 SSH/`scp`。**本桥省的是宿主的推理与 token，不是调用方的上下文。**

## 一处容易误解的地方

「不经过模型」指的是**宿主**这一侧：桥只做「收请求 → 跑工具 → 回结果」，宿主不调用任何 LLM API。**调用方那侧的模型照旧要推理**，它只是把推理用来决定「调哪个工具、传什么参数」，而不是用来「看屏幕、算坐标」。所以两边的 token 账要分开算。

同理，`tools/call` 在宿主侧可能停在审批弹窗上——宿主无交互 UI 且该工具审批为 `prompt` 档时，请求会一直挂起（实测 ≥90s），调用方必须自设超时。此时审计日志里该调用只有 `start` 没有 `done`，见 README「审批」。

## 两者不冲突

它们解决的是不同问题，可以叠加：

- 目标只有 GUI、没有可调用的接口 → computer use 是唯一选择
- 目标是宿主那侧的文件、shell、已注册的工具 → 本桥直接暴露，不必截屏
- 调用方既要调工具、又要点某个界面 → 先经 MCP 拿工具，再用 computer use 操作剩下的界面

判据很简单：**能落到工具上的就别截屏。** 工具调用是确定性的、可审计的、不占宿主的 token；截屏是这三样都不是。

## 边界

本桥只暴露 `tools/list` + `tools/call`，没有 resources、没有 prompts、不做键鼠注入——它不实现 computer use 的那一半，也不打算实现。固定路由到宿主 `Main` 会话。完整 wire 契约见 [协议参考](./protocol.md)，暴露面与威胁模型见 [使用指南](./intro)。
